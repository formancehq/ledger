# ACME-dev Pebble versus RocksDB benchmark protocol

## Purpose and scope

Compare the pre-RocksDB Ledger v3 revision (`c6a99fc92f43f5127c898fd9a727adee3424310d`) with a pinned RocksDB revision on ACME-dev. Measure writes first, then reads over equivalently populated stores. This is a fresh-data comparison: each engine gets its own disposable three-node deployment, logical ledger and PVCs. No Pebble-to-RocksDB data conversion is involved.

Record the exact Git SHA, image digest, operator version, CRD version, k6 archive checksum and benchmark configuration for every run. Do not use mutable image tags as the run identity. The existing single-node CI comparison in `docs/technical/architecture/subsystems/storage/performance-comparison.md` is a useful smoke test, but its campaign-to-campaign latency variation and limited rates do not establish cluster throughput or parity.

A [beta.5 pilot completed on 2026-09-30](../../docs/technical/architecture/subsystems/storage/acme-pebble-beta5-pilot.md) with three replicas: 100 and 1,000 transactions/s write windows, then validated reads. It found no workload errors; the Benchmark operator's Grafana snapshot reporting failed because its URL was not configured. Fix that configuration before the full campaign. The pilot uses mixed shared hosts and a small warm-cache dataset, so it establishes neither engine parity nor maximum capacity.

## Existing harness and ACME-dev preflight

- `tests/perf/main.go` packages a k6 script and creates a `Benchmark` resource with its Cluster/Ledger prerequisites. The report is a `k6-report-<testrun-name>` ConfigMap as described in `tests/perf/README.md`.
- `Pulumi.acme.yaml` currently provisions one Ledger replica, uses `world_to_bank`, bulk size 50 and Numscript, and contains `spec.config.pebble`. Its `K6_STAGES` load is a VU-based, closed-loop workload. The shared success check verifies only HTTP 200, and its error threshold permits 10%. These defaults are insufficient for a comparative decision.
- ACME-dev currently has three existing, three-replica Ledger Clusters in `ledger-v3`. Treat them as unrelated workloads and leave them untouched. The installed Ledger operator is `v3.0.0-beta.5`; the live Cluster CRD has `spec.pebble` and no `spec.rocksdb`. The RocksDB operator is being isolated under `ledger-next.formance.com/v1alpha1` with its own Helm release and workload namespace. Keep the Pebble operator and old CRDs in place; install the new chart as a separate release rather than upgrading the old one. The Pebble benchmark uses old-group Cluster/Ledger CRs, and the RocksDB benchmark uses new-group CRs. Validate both effective engine configurations and the operators' isolated ownership before measuring. The latest published Pebble beta pilot provides early workload and capacity feedback, but the final A/B comparison must use the pinned pre-RocksDB commit to distinguish engine changes from unrelated beta-to-PR changes.
- The `io2` StorageClass is backed by the EBS CSI driver and currently sets 5,000 IOPS. ACME-dev has mixed node architectures and sizes. Select one node architecture and comparable instance type for all measured Ledger and k6 pods; record placement, EBS volume size, IOPS and throughput. Check spare capacity and background load before scheduling the campaign.
- A local `pulumi` executable is not currently available in this workspace. Before execution, use the repository's Nix environment and confirm `pulumi`, `k6`, cluster access and image pullability.

## Controlled setup

1. Build Pebble and RocksDB Linux images from the pinned commits, with the same build settings and target architecture. Pin the exact image digests in the benchmark manifests. Keep the k6 image and archive identical across engines.
2. Create dedicated benchmark names, ledger names and PVCs. Use the same three-replica Raft topology, CPU/memory requests and limits, cache budgets, Raft settings, storage class, IOPS/throughput and node placement for both engines. Record unavoidable engine-specific settings (such as compaction defaults); do not claim byte-for-byte equivalent cache configuration. Do not reuse any existing Ledger PVC or the three live Ledger Clusters.
3. Run engines **sequentially** so they do not contend for CPUs, EBS bandwidth or network. Alternate the order across paired repetitions (Pebble–RocksDB, RocksDB–Pebble, and repeat) to reduce time-of-day bias. Recreate fresh stores for each independent write trial. Make PVC ownership and cleanup explicit in each operator benchmark manifest; the old ACME example requests PVC deletion on teardown. Export all reports before cleanup and restrict deletion to the dedicated benchmark resources.
4. Use a deterministic workload version and seed. Keep payload size, atomic mode, Numscript/postings choice, account-cardinality distribution, request rate, duration and client placement fixed for each pair. Validate response bodies and committed transaction counts, not only HTTP status.

## Phase 1: writes

Use `world_to_bank.js` with 50 atomic Numscript transactions per bulk as the first scenario because this is the existing ACME load. Add a second scenario based on `any_unbounded_to_any.js` to grow account cardinality and the read index. Keep `single_hot_account.js` as a separately reported contention scenario, not mixed into the primary result.

For the comparison harness, use k6's open-loop `constant-arrival-rate` executor and explicit per-scenario request rates. Start below the sustainable range identified by a short pilot, then increase through the knee until latency rises sharply or errors/dropped iterations begin. At each common offered rate, use 1 minute of warmup and at least 5 minutes of measured load. Repeat every valid pair at least four times, alternating the first engine. Report committed transactions per second (bulk size times successful, fully validated bulks), request throughput, p50/p95/p99 latency, errors, timeouts and dropped iterations. The maximum sustainable rate is the highest **common** rate where both engines satisfy the validity criteria; also report each engine's own limit.

The fixed-`K6_STAGES` VU scenario can be retained as a secondary, user-style throughput test. Do not derive capacity or latency equivalence from it: a slower server makes a closed-loop client send fewer requests.

## Phase 2: reads

The repository has no dedicated ACME read workload. Add one using the existing Ledger v3 HTTP endpoints: account point reads (`/v3/{ledger}/accounts/{address}`), transaction point reads (`/v3/{ledger}/transactions/{id}`), and account/transaction list queries with a fixed page size and filters. Measure these separately so a broad list scan cannot hide a point-read regression. The local `scripts/storage-performance-api.js` provides a starting point for k6 metrics and validation, but its `/accounts?pageSize=20` call alone is not sufficient.

Populate each fresh engine by replaying the same logical write stream, rather than copying storage files. Size the broad-keyspace dataset above the effective block-cache capacity and record the resulting on-disk footprint. Verify matching transaction and account counts, selected balances and sampled transaction responses. Wait for indexed reads to expose the expected records before measuring; record this catch-up time separately. Stop writes during the primary read test. Use a deterministic mix of existing account and transaction IDs, including hot and broad-keyspace samples, and the same request order/seed for both engines. Measure both warm-cache reads and a separately labelled cold/restarted-cache pass on the disposable Clusters. Use open-loop rates, 1 minute warmup, at least 5 minutes measured, and four paired repetitions per rate with alternating first engine. Add a mixed read/write phase only after the isolated write and read results are understood.

## Telemetry, validity and decision

Capture the k6 JSON/CSV summary and Benchmark report, pod/container CPU and RSS, CPU throttling, restarts, Raft leader changes and proposal/apply lag, index catch-up, EBS IOPS/throughput/latency, PVC growth, and RocksDB/Pebble flush, compaction and write-stall metrics where exposed. Keep time-aligned Grafana/Prometheus snapshots and record other cluster activity. Run the load generator away from saturation; otherwise client CPU, network or VU limits become the bottleneck.

Invalidate a measured run if it has any unexpected request/application error, dropped iteration, pod restart, leader change, client saturation, severe CPU throttling, an unmatched effective configuration, or materially different background load. Investigate such runs rather than averaging them in. Compare paired medians and the spread of p95/p99 and throughput at each **equal offered load**, with raw per-run values attached. Report the saturation knee separately. The earlier CI results changed ranking between otherwise similar campaigns, so a single winning run is not evidence of parity. Agree on acceptable regression limits after seeing the stable-load baseline and before choosing the final release decision; do not silently call a noisy result “ISO”.

## Execution handoff

Before launching, prepare separate old-group and next-group Cluster/Ledger benchmark manifests and install the next operator as a new release, confirm image digests, decide the matched three-node resource profile and dataset size from ACME capacity, implement the strict k6 write/read scripts, and save the two benchmark manifests plus a run matrix. Preview every resource change. Keep the current `Pulumi.acme.yaml` as historical input until a benchmark-only configuration is reviewed; applying it unchanged would test a one-node Pebble-shaped setup. Execute the campaign only after the preflight passes, then publish the raw reports and a paired comparison table.
